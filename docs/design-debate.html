R2 — Epsilon-withholding is the clearest bad proposal. Claude correctly observes that causal “strength” requires a counterfactual, then proposes turning production users into a noisy within-subject experiment. Withholding a known preference 15% of the time deliberately degrades behavior, provides almost no signal when feedback is absent, and is confounded by history: users remember previous compliance, so turns are not independent experimental units. It also does not yield a defensible SC-10 benchmark “for free”; production traffic lacks controlled ground truth and comparable task difficulty.

Alternative: remove causal strength from v0.1. Use one belief score derived from explicit statements, corrections, and reversals. Demonstrate causal impact in an offline randomized harness: same scripted user state and prompts, hint enabled versus disabled, deterministic checker, repeated across seeds. R3 — The explicit→confidence / implicit→strength split is semantically wrong. Explicit evidence can say how strongly a preference should influence behavior: “Always return complete files” differs from “I usually prefer complete files.” Conversely, implicit correction can be strong evidence that a preference exists: repeatedly asking for the full file immediately after receiving a patch is not merely a utility signal. Most importantly, silence is evidence of neither existence nor utility. Calling non-complaint “implicit positive” manufactures data.

Alternative: classify only observable signals: direct preference, direct reversal, corrective follow-up, accepted/rejected action, and no-signal. Each signal has bounded effects determined by polarity, specificity, and applicability. Never learn from silence. Cap repeated implicit evidence to one event per task/session. For v0.1, direct statements and corrective follow-ups are enough.

R4 — AGREE.

R5 — Pure projection is directionally right but overstated. replay(evidence_log, params) gives free threshold sweeps only when changing reducer parameters. It does not give free re-extraction when prompts, models, taxonomies, scope classification, or normalization rules change; those require replaying raw experiences and potentially new LLM calls. An append-only log also conflicts with “forget me” and deletion obligations. Finally, outcomes and evidence are not necessarily duplicates: an outcome is a raw observation; evidence is an attributed interpretation of that outcome.

Alternative: retain immutable raw experiences/outcomes until deletion, plus versioned derived evidence. Make pattern state a deterministic rebuildable projection keyed by extractor_version, taxonomy_version, and reducer_version. On user deletion, physically delete all owned raw and derived records and rebuild affected projections. Drop the provenance array and habits table, but do not conflate raw outcomes with interpreted evidence.

R6 — Specialization-on-contradiction is unsafe and benchmark-hostile. Starting every preference as general guarantees overgeneralization until the user complains. That is precisely the failure the system claims to prevent. Contradictions may also be too sparse to support a statistically meaningful split, and “general plus exception” introduces precedence semantics Claude does not specify.

  • For corrective follow‑ups, the same delay applies: a single corrective turn in session i does not activate; a second corrective turn in a later session is required.

Is the trade a win for the user? Measure the cost of wrong activation. A false positive injected by C persists until the user detects it and issues a direct reversal. That requires at least one full turn of the user noticing the erroneous output and explicitly saying “no, give me diffs”. In a stream with a realistic false‑positive rate of 10–20%, the number of correction turns per week can exceed the number of new genuine preferences. The cumulative user annoyance and trust erosion outweigh the 1‑session activation delay. Moreover, ASC can surface the pending evidence to the user (“I’ve noticed you might prefer X, is that correct?”) in a future release, further reducing the delay. For v0.1, the precision gain is unequivocally a net win.

3. Fixed reducer

The previous reducer was last‑write‑wins because direct_statement jumped to support_level=2 immediately. The corrected design:

State. For each (user_id, key, normalized_value, scope) keep support_level ∈ {0, 1, 2} and activation_requires = 2.

Evidence ingestion. Each session contributes at most one increment to support_level for a given tuple. The reducer processes at most one evidence event per session per tuple.

  • Confidence gate: Only evidence with extractor_confidence >= 0.85 and quotation == false and scope != unknown is eligible to increment. This eliminates low‑confidence and quoted noise. (Lower‑confidence extractions are stored but do not affect state.)
  • direct_statement: If eligible, increment support_level by 1 (capped at 2). If support_level reaches 2, the preference becomes active.
  • corrective_follow_up: Treated identically to direct_statement for increment purposes.
  • explicit_rejection: Set support_level = 0, immediate deactivation.
  • direct_reversal: Set old value support_level = 0; if a replacement value is explicitly stated, treat it as a new direct_statement starting at support_level = 1 (requires a second session to activate).

Mutual exclusion. Activating a value at a given key and scope sets all other values for that key/scope to support_level = 0 and deactivates them.

What makes a single statement sufficient? Nothing. A single direct_statement never reaches support_level=2 on its own. Two independent sessions with corroborating evidence are required. This is the price of noise immunity. The design can later be extended with a configurable activation_threshold (e.g., 1 for high‑trust domains) but v0.1 hard‑codes 2 to ensure the precision claim is testable.

4. Final call

This does not ship as “artificial subconscious.” The subconscious framing implies autonomous belief formation from implicit signals, which v0.1 does not attempt. The system is a structured preference memory with confirmation‑based activation, correction handling, and versioned evidence.

The one‑sentence spec claim: “ASC extracts explicit user preferences across sessions, activates them only after corroboration from two independent interactions, and resists injection from noisy or quoted statements, providing a verifiable precision-over-noise trade‑off.”

def chat(messages, user_id, session_id, task_scope):

6. CHECKERS

AREA · "FULL_FILE_MARKER vs DIFF_MARKER" is hand-wavy. Model output mixes prose, fences, partial diffs.

DECISION: The concrete detection rules are:

  • FULL_FILE_MARKER: Output contains a code fence with a header that does not contain diff, patch, +/- line prefixes, @@ hunk header, or ---/+++ file header. AND the fenced content is ≥5 lines. AND the fence does not contain ellipsis markers (..., …).
  • DIFF_MARKER: Output contains a code fence where ≥30% of lines start with +, -, or (unified diff prefix), OR the fence header contains diff/patch, OR the content contains @@.
  • Paragraph count: Split on \n\n, count groups of non-whitespace text. A paragraph is ≥2 sentences or ≥1 sentence + code fence.
  • Output language: Count tokens in each language using a simple dictionary match (stopwords + common words). Language with >60% tokens wins. For Persian: count tokens containing Unicode ranges \u0600-\u06FF.
  • Failure modes: Ambiguous output (a complete file wrapped in a diff header) → checkers tiebreak in favor of DIFF_MARKER (false positive for "did not activate"). A prose description of a complete file without a fence → checker returns "no marker detected" → measured as "no preference applied" even if the model semantically complied.

COST: Simple string checks miss semantic compliance and penalize models that comply without using the literal format.

RISK: The benchmark measures the model's format-following, not genuine preference compliance. If ASC injects "give me complete files" and the model outputs a complete file without a code fence, the checker says ASC failed. This is a measurement validity threat. Document it in the benchmark report.

7. HARNESS SEAM

AREA · "Extractor output is scripted in the harness." Then what's under test, and what class of bug is structurally invisible?

DECISION:

  • What's under test: The reducer, precedence logic, session-gating, scope-gating, and injection rendering. The extractor is not under test in the headline scenarios.
  • Structurally invisible bug: Extractor recall failure. A real extractor missing a durability statement that the script said "should be detected" → reducer works perfectly on garbage input → benchmark passes, real system fails. Also: extractor false-positive on noise → reducer sees gold input in benchmarks but sees garbage in production.

COST: Doubles the benchmark matrix. Real extractor will produce numbers strictly worse than scripted, and the delta is the extractor's error contribution — that must be reported.

8. PERSISTENCE

AREA · FastAPI async + SQLAlchemy sync + SQLite single-writer. Concurrency model is unspecified.

DECISION:

  • WAL mode: SQLite in WAL journal mode (PRAGMA journal_mode=WAL). Readers do not block a single writer.
  • Concurrency model: One FastAPI process. SQLAlchemy with check_same_thread=False and a single Queue-based writer thread. All DB writes are dispatched to the writer thread via queue.put(). The FastAPI route returns a 202 Accepted with the idempotency_key immediately; the caller polls or trusts eventual consistency.
  • Transaction boundaries: One transaction per turn ingest: INSERT INTO experiences, INSERT INTO evidence, INSERT OR UPDATE INTO preferences (reducer projection) — all in one serialized transaction in the writer thread.
  • Idempotency key: Generated as hashlib.sha256(user_id + session_id + turn_id + utc_timestamp).hexdigest()[:16] by the caller, or ASC generates it from the same tuple if the caller omits it.
  • Reducer runs: In the writer thread, inside the same transaction.
  • Failure mode when turn arrives before previous evidence written: The writer queue serializes. The second turn's transaction blocks until the first commits. No deadlock because single writer. If the queue grows (e.g., user spamming turns), latency grows linearly; v0.1 has no backpressure mechanism.

COST: Adds a polling requirement for the caller to confirm ingest, or a webhook later. The single-writer thread limits throughput to ~100 turns/second on SQLite, which is sufficient for single-user.

RISK: If the writer thread crashes, the entire pipeline halts without alerting. A turn that produces extractor output but fails the DB transaction loses the evidence silently unless the caller retries with the idempotency key. The experiences.processing_status field must be set to "pending" on 202 and "complete" on successful transaction; the caller can query GET /experiences/{id} to confirm.

9. REPLAY PURITY

AREA · replay(evidence, params) must be pure. Ordering, clock skew, ties, and param storage break purity silently.

DECISION:

  • Ordering guarantee: Within a session, evidence is ordered by created_at. Across sessions, sessions are ordered by id (auto-increment) in replay. The reducer processes evidence grouped by (user_id, session_id) ordered by session.created_at (using experiences.created_at for the session's first turn), then within session by evidence.created_at.
  • Tie-breaking within a session: If two evidence events have the same created_at (same transaction), tiebreak by evidence.id ascending.
  • Clock skew: created_at uses datetime.utcnow() from the writer thread (single clock). No NTP sync needed for single-user.
  • Param storage: params = {extractor_version, taxonomy_version, scope_classifier_version, reducer_version, calibration_thresholds}. These are stored in a versions config table or hardcoded in a params.json accompanying the replay. The replay function reads them as input arguments, not from mutable state.
  • Bit-identical replay: Requires (a) evidence rows unchanged, (b) same params, (c) same ordering function, (d) no external randomness (no model calls in reducer). The reducer as specified (state machine with deterministic immediate-activation gate) is pure.
  • Silent break: Adding a created_at default that uses datetime.now() per row in SQLAlchemy with millisecond precision → two rows from the same transaction get different timestamps → tiebreaking changes → replay diverges. Fix: use explicit timestamp assignment in the writer thread with datetime.utcnow().replace(microsecond=0) for all rows in one transaction.

COST: replace(microsecond=0) limits resolution to 1 second, which is fine for human-speed chat.

RISK: If someone later adds a "background re-derivation" that processes evidence async while new evidence arrives, the ordering between old and new evidence changes because sessions are no longer processed in strict insertion order. Replay purity requires a snapshot at a point in time; live re-derivation is not pure.

10. VERSION BUMPS

AREA · What does bumping taxonomy_version actually cost on 10k experiences?

DECISION:

  • Cost: Re-running the extractor over 10k experiences. Each requires one model call to re-extract with the new taxonomy. At 10k × $0.001/call = ~$10 in API cost and ~33 minutes at 5 calls/sec. If the extractor model is self-hosted, cost is compute time only.
  • Mechanism: A migration script (an offline job), not a background task. The script:
  1. Reads all experiences rows .where(processing_status == 'complete').
  2. For each, calls the new extractor, writes new evidence rows with taxonomy_version = new, extractor_version = current.
  3. Runs replay(all_evidence, params) to rebuild preferences with the new taxonomy_version.
  4. Old evidence rows are NOT deleted (versioned, append-only).
  • Scope classifier bump: Same pattern, but re-running only the scope classifier over existing evidence, not re-extracting.

COST: 10k is small enough for an offline script. At 100k, the migration takes ~5.5 hours; needs a progress bar and a checkpoint/resume mechanism to survive interruption.

RISK: While the migration runs, new experiences continue to arrive at the current version. The rebuilt projection is stale as soon as the migration finishes unless the migration also processes experiences created during the migration window. 2. Authority ladder

“Reversible in seconds and embarrasses nobody” is not an operational test. Reversal may require physical access, knowledge, connectivity, or noticing the mistake. Embarrassment is subjective and misses privacy, safety, financial, and household effects. Classify by worst plausible consequence, not typical convenience.

Three listed level-3 actions that are actually level 4 by default:

The mother is not a schema field. If she did not read, understand, and consent, the system cannot legitimately infer authority to act for her from the operator’s ownership of the box.   • Principal: whose body, account, property, data, or interests are affected.
  • Operator: who configures or physically uses the system.

4. Emergency button

A pre-loaded call is not “90% of the value” unless its failure modes are explicit. Accidental taps can place a real emergency call; preventing all accidental taps with a one-tap design is impossible. Stale allergies, medications, contacts, or diagnoses can mislead responders. A cached location can be wrong after travel, indoors, or during a network failure. A user may reasonably believe the product detects emergencies or is monitoring them when it does neither.

Change §9 and the UI:

  • Do not call it an emergency system or imply coverage; show “manual shortcut only—no detection or monitoring.”
  • Resolve and display current location at activation, with timestamp and failure state; never silently substitute stale location.
  • Show medical data timestamps and require confirmation that it is current; pass “may be stale” to responders.
  • Use press-and-hold or a clearly deliberate two-step confirmation, with a short cancel window, while preserving an accessible urgent path.
  • Define jurisdiction, number, language, network failure, accidental-call cancellation, and what happens if the call disconnects.
  • Test false taps, stale data, wrong location, travel, shared-device use, and users who cannot speak.

5. Trust collapse

The most likely first irreversible trust failure in v1 is a false VERIFIED research result. It directly violates the product’s central promise that the user need not check the work, and the success criterion requires zero such errors. An attacker can also seed a plausible source through email or a fetched page.

Prevent it by making VERIFIED a typed evidence state, not a model label. Every claim must identify the exact claim span, source identity and retrieval time, quoted supporting evidence, transformation performed, and a reproducible check. Claims requiring external truth, judgment, or source credibility must remain FOUND or UNRESOLVED. A deterministic validator, not the synthesizing model, assigns VERIFIED; absence of required evidence is a hard failure. Add adversarial release tests and prohibit the model from relabeling FOUND content.

6. VERIFIED versus FOUND

The separation is implementable only for narrowly defined verification procedures. “The system verified this itself” cannot mean “a model found a source that agrees.” For a research claim, it must mean a declared procedure succeeded: exact identifier resolution, source retrieval, quote-span match, arithmetic recomputation, code/test execution, or independently reproduced observation.

Add a verification-type enum and required evidence schema. Do not permit a generic VERIFIED state. The UI must show procedure, evidence, timestamp, and limitations. A claim must downgrade to FOUND when the source is inaccessible, stale, ambiguous, derivative, or merely corroborative. Enforce this in code and release tests; never let the synthesis model choose the label.

  • User answers waiting_user late: Check lifetime.until. If past expiry, transition to expired and discard the input. If valid, transition to running to process the answer, then to returned.
  • Two intentions match the same event: Both fire independently. They do not share state, context, or budget.

2. Triggers: Mail Mechanism

"Event" is implemented as follows:

  • Transport: IMAP IDLE for push. Fallback to 5-minute polling if the connection drops.

  • Budget Unit: USD cents (integer).

  • Abandoned vs. Slow: Governed by two independent limits. Budget (cents) and Wall-clock (milliseconds, default 300,000). If budget hits first, it is returned (exhausted). If wall-clock hits first, it is suspended (timeout/abandoned) to prevent zombie processes.
